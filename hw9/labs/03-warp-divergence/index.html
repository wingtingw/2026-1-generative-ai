目標

理解為什麼同一個 warp 裡的 thread 走不同的 if/else 分支會變慢，以及怎麼讓分支條件「對齊 warp」。

概念

GPU 用 SIMT（Single Instruction, Multiple Threads）的方式執行：一個 warp 的 32 個 lane 在同一時間執行同一道指令。 如果遇到 if，而 warp 裡有些 lane 條件成立、有些不成立，硬體沒辦法同時跑兩條路，只好輪流執行： 先跑 if 那條路（不成立的 lane 被遮蔽、閒著），再跑 else 那條路（換另一批 lane 閒著）。這就是 warp divergence（warp 分歧）。

重點是「同一個 warp 內」。如果整個 warp 的條件都一樣，例如用 threadIdx.x / 32（warp 編號）來分支， 每個 warp 只會走一條路，就完全沒有分歧。

SIMT 效率 = 有在工作的 lane 次數 ÷ (32 × 實際執行的路徑數)

互動區

把滑鼠移到 lane 上看詳細資訊

簡化假設：一個 block 有 64 個 thread（2 個 warp），if 和 else 的工作量一樣。沒有任何 lane 要走的路徑會被直接跳過，不花時間。

Kernel 程式碼

__global__ void branchy(float* a) {
    int tid = threadIdx.x;
    if (tid % 2 == 0) {        // ❌ 每個 warp 裡一半成立、一半不成立 → 兩條路都要跑
        a[tid] = pathA(a[tid]);
    } else {
        a[tid] = pathB(a[tid]);
    }
}

// ✅ 改成以 warp 為單位分支：同一個 warp 的 32 個 lane 條件相同
int warpId = threadIdx.x / 32;
if (warpId % 2 == 0) { /* pathA */ } else { /* pathB */ }

常見誤區

  • 「有 if 就一定會 divergence」：只有同一個 warp 內的 lane 意見不一致才會。條件在整個 warp 一致（例如以 warp 編號或 blockIdx 分支）就沒有代價。
  • 「divergence 會讓結果算錯」：不會，結果一樣正確，只是慢。被遮蔽的 lane 只是在那段時間不寫入結果。
  • 不同 block 之間也會互相拖累：不會。divergence 是 warp 內的事，不同 warp、不同 block 各自排程。

很短的分支，編譯器可能直接改成 predication（兩邊都算、再挑結果），所以實測不一定會看到明顯差距。分支裡的工作越多，divergence 的代價越明顯。

自我檢查

條件 tid < 16，64 個 thread，總共要執行幾條路徑？SIMT 效率多少？
warp 0 一半成立一半不成立，要跑 2 條；warp 1 全部不成立，只跑 else 1 條。共 3 條路徑，效率 = 64 ÷ (32 × 3) ≈ 66.7%。
條件 tid < 32 和 tid < 40，哪一個有 divergence？
tid < 32 剛好切在 warp 邊界，沒有 divergence（100%）；tid < 40 讓 warp 1 的前 8 個 lane 成立、後 24 個不成立，warp 1 要跑兩次。
資料相依的條件（例如 a[tid] > 0）要怎麼減少 divergence？
常見做法是先把資料排序或分組，讓同類的資料落在同一個 warp，或是重寫成不需要分支的算術（例如用 fmaxf 取代 if）。
