目標

看懂一個 warp 的 32 個 thread 同時讀 global memory 時，存取模式如何決定 GPU 實際要搬多少資料。

概念

GPU 以 warp（32 個 thread 一組）為單位執行指令。當一個 warp 執行一道讀取指令時，32 個 lane 各自要一個位址， 硬體會把這些請求合併（coalesce）成最少的記憶體交易。global memory 的最小搬運單位是 32 bytes 的 sector， 只要一個 sector 裡有任何 1 byte 被用到，整個 32 bytes 都會被搬進來。

如果 32 個 lane 讀的是連續、對齊的 float（4 bytes），總共 128 bytes，剛好 4 個 sector，一點都沒浪費。 但如果每個 lane 間隔 stride 個元素去讀，同樣只用到 128 bytes 的資料，卻可能要搬 32 個 sector（1024 bytes）。

位址(lane) = (lane × stride + offset) × sizeof(T)　　效率 = 請求的 bytes ÷ (sector 數 × 32)

互動區

把滑鼠移到 lane 或 sector 上看詳細資訊

這裡是簡化模型：只計算一個 warp、一道讀取指令碰到幾個 32-byte sector，不考慮 cache 命中與其他 warp 的重複使用。

Kernel 程式碼

__global__ void stridedCopy(const float* in, float* out,
                            int stride, int offset) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    // stride = 1、offset = 0：同一個 warp 讀連續位址 → 完全 coalesced
    // stride 變大：lane 之間的位址拉開 → 碰到更多 sector，頻寬被浪費
    out[i] = in[i * stride + offset];
}

常見誤區

  • 「每個 thread 只讀 4 bytes，所以很省」：硬體搬的是整個 sector。stride 夠大時，每個 lane 都獨占一個 sector，實際流量是需要的 8 倍。
  • 2D 陣列用錯方向走訪：C/CUDA 是 row-major。讓相鄰 thread 處理同一 row 的相鄰欄（col = threadIdx.x），讀取才會連續；反過來讓相鄰 thread 走同一欄，就等於 stride = 寬度。
  • 以為只要沒有 stride 就一定最好：起始位址沒有對齊（offset ≠ 0）也會多碰一個 sector。效率從 100% 掉到 80%，雖然不嚴重，但在頻寬瓶頸的 kernel 裡看得出來。

自我檢查

float、stride = 2、offset = 0，一個 warp 會碰到幾個 sector？效率多少？
位址橫跨 0～248 bytes，共 8 個 sector（256 bytes），只用到 128 bytes，效率 50%。
stride 從 8 調到 32，sector 數還會增加嗎？為什麼？
不會。float 的 stride = 8 時相鄰 lane 已經差 32 bytes，每個 lane 各自落在不同 sector，總共 32 個，已經是一個 warp 的上限。再拉大 stride 只是 sector 離得更遠。
把型別換成 double、stride = 1，效率還是 100% 嗎？
是。32 × 8 = 256 bytes，剛好 8 個 sector，沒有浪費。只是一次要搬的量變成兩倍。
